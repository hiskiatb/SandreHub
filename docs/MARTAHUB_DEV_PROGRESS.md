### Keputusan teknis penting (menjawab gap 13 — verifikasi teknis link-folder-lokal)

Spec §9.1 mengusulkan mekanisme "link folder lokal" lewat **File System Access API** (browser mengingat *handle* folder, browse isi folder dari web) — tapi API ini **hanya didukung Chrome/Edge**, tidak Firefox/Safari, dan (diakui sendiri oleh spec) izin akses filenya **tidak bisa permanen** — user tetap harus grant ulang tiap sesi browser. Karena keuntungan riil dari File System Access API (browse folder tanpa file-picker) nyaris hilang oleh batasan izin-ulang-tiap-sesi ini, sementara kompatibilitas browsernya jauh lebih sempit, **diputuskan pakai `<input type="file">` biasa** (didukung SEMUA browser) sebagai gantinya — pengguna tetap harus memilih file tiap sesi baik dengan API lama maupun baru, jadi tidak ada kehilangan UX yang berarti. Yang benar-benar disimpan sebagai "diingat" (lewat `mh_local_folder_links`) adalah **metadata pemetaan kolom** (nama file terakhir, kolom mana = site_id/lat/lng) — BUKAN file itu sendiri atau handle folder — supaya sesi berikutnya user tidak perlu memetakan ulang kolom dari nol, cukup pilih ulang filenya. Prinsip §0.2 (file mentah tidak pernah ke server) tetap terjaga karena parsing & pencocokan 100% terjadi di browser; hanya HASIL pencocokan yang dikirim ke database. Keputusan ini dicatat di sini untuk direview user bila ternyata browsing-folder-tanpa-repick memang dibutuhkan nanti.

### Bug ditemukan & diperbaiki SEBELUM fitur ini dibangun (kritis, memengaruhi Fase 1 juga)

**Ditemukan sendiri saat menyiapkan RPC folder-link**: RPC web (`mh_set_setting` dari Fase 1, dan rencana RPC baru Fase 3) memverifikasi role pemanggil lewat `auth.uid()`. Ternyata **web (tracehub) TIDAK PERNAH membuat sesi Supabase Auth asli ke project MartaHub** — login web sepenuhnya lewat SandraHub (`lib/supabase.js`), identitas dijembatani ke MartaHub HANYA lewat pencocokan **email** ke `mh_profiles` (`getMartaScope`, dipakai konsisten di semua halaman web MartaHub lain). Query pembuktian: `supabaseMarta` (client di web) memakai anon key TANPA sesi — dikonfirmasi lewat `information_schema.role_routine_grants` yang menunjukkan RPC lain (`mh_assign_user`, dst.) memang dieksekusi sbg role **`anon`**, bukan `authenticated`. ## Fase 8 — Skor Geo Compliance ✅ SELESAI (27 Juli 2026)

**Spec:** §8.3, gap 34. **Prasyarat:** Fase 3 (event tervalidasi) & Fase 5 (MD Activities/Street Branding) — sumber evidence-nya. **PERINGATAN dari spec:** formula ditandai draft, minta direview ulang sebelum kode — 3 pertanyaan terbuka dikonfirmasi/diputuskan sebelum implementasi (lihat di bawah).

### Keputusan yang dikonfirmasi/diambil di fase ini

- **Pembobotan antar 3 sumber evidence** (event tervalidasi, MD Activities mode Activity/Outlet, review Street Branding) — spec tidak merekomendasikan angka pasti, hanya menyinggung kemungkinan Street Branding dibobot beda karena manual. **Ditanyakan eksplisit ke user** (AskUserQuestion) sebelum kode ditulis, mengingat ini formula evaluasi kinerja yang berdampak ke penilaian orang sungguhan — **dikonfirmasi: sama rata/pooled**, tanpa bobot berbeda per sumber. Ini juga pembacaan paling sederhana dari formula dasar spec (persentase dari total, bukan rata-rata tertimbang custom).
- **Metode agregasi berjenjang antar level** — spec merekomendasikan "rata-rata berbobot jumlah evidence". Diimplementasikan lewat wawasan matematis: kalau skor level atas = SUM(valid) / SUM(total) dari seluruh subtree (bukan rata-rata dari skor individu anak buah), itu **otomatis setara** dengan rata-rata berbobot-jumlah-evidence — sekaligus otomatis memenuhi syarat spec lain ("tiap level lihat skor sendiri PLUS agregat tim di bawah") karena evidence milik level itu sendiri ikut di-pool bersama evidence seluruh keturunannya.
